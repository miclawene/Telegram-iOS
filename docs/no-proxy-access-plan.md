# План: Telegram без прокси и VPN

Цель: пользоваться Telegram в РФ так, чтобы на телефоне **не было ни VPN-профиля, ни
настроек прокси**, и чтобы для провайдера/DPI трафик выглядел как обычный HTTPS к
нейтральному домену.

Документ описывает, что для этого нужно, что в репозитории **уже готово**, где
**главный пробел**, и две развилки реализации с оценками.

---

## 1. Диагноз: что на самом деле нужно менять

Первоначальная идея была «пусть сообщения грузятся на мой сервер, а приложение читает
с него». Для заявленной цели это **не нужно и вредно**.

Разберём, почему. Есть два принципиально разных способа задействовать свой сервер:

| | **Транспорт** (релей/прокси) | **Зеркало** (свой сервер хранит сообщения) |
|---|---|---|
| Что видит сервер | Зашифрованный поток MTProto, **прочитать переписку не может** | **Всю переписку в открытом виде** |
| Секретные чаты | Работают | Не работают (ключи привязаны к устройству) |
| Звонки | Работают | Не работают |
| Push-уведомления | Работают штатно | Нужен свой APNs-сертификат и своя реализация |
| Объём работы | Дни–недели | Месяцы |
| Риск блокировки аккаунта | Нет | Есть (постоянная сессия с датацентра, `FLOOD_WAIT`) |
| Решает «без прокси и VPN» | **Да** | Да |

Важное: своего «сервера Telegram» не существует — серверная часть закрыта. Аккаунт
физически всегда живёт на дата-центрах Telegram. «Свой сервер» может быть только
транспортом либо постоянно работающим клиентом-зеркалом.

**Вывод: для цели «без прокси и VPN» нужен только транспорт.** Сообщения по-прежнему
идут с серверов Telegram, лежат на устройстве, вся функциональность сохраняется.
Зеркало — ответ на другую задачу («чтобы на изъятом телефоне ничего не было»), и оно
ухудшает приватность, потому что сервер видит plaintext.

Отдельно стоит зафиксировать: облачные чаты Telegram **и так не хранятся в РФ** — они на
дата-центрах в Амстердаме, Майами и Сингапуре. Свой сервер меняет не юрисдикцию
хранения, а только то, куда идёт TCP-соединение с телефона.

### Что значит «без прокси» технически

«Без прокси и VPN» не означает «без промежуточного сервера» — без него обойти
блокировку невозможно. Означает три требования:

1. **Нет VPN-профиля** в настройках iOS (не привлекает внимания при досмотре, не
   ломает остальной трафик, не жрёт батарею).
2. **Ничего не надо настраивать руками** — адрес сервера вшит в сборку, failover
   автоматический.
3. **Трафик неотличим от обычного HTTPS** — валидный TLS к домену с настоящим
   сертификатом и настоящим сайтом-заглушкой на `/`.

## 2. Что уже готово в репозитории

### 2.1 Релей-сервер — готов

`relay-server/` содержит рабочий WSS→TCP релей. Это **прозрачный байтовый пайп**:

- `relay-server/server.js:188` — `ws.on('message')` → `tcpSocket.write(data)`
- `relay-server/server.js:198` — `tcpSocket.on('data')` → `ws.send(chunk, { binary: true })`
- Выбор дата-центра путём URL: `/dc/<1-5>`, карта DC в `server.js:40`, переопределение
  через `DC_LIST`
- Опциональный `?token=` (`server.js:167`), лимит соединений, метрики, без логирования
  payload

Поскольку это байтовый пайп, **шифрование MTProto остаётся сквозным между телефоном и
дата-центром Telegram**. Оператор релея переписку прочитать не может — принципиальное
преимущество перед зеркалом.

### 2.2 Маскировка — готова

`relay-server/nginx.conf`:
- TLS 1.2/1.3 с Let's Encrypt (`nginx.conf:45-57`), OCSP stapling, session tickets off
- WebSocket-upgrade только на `^/dc/[1-5]$` (`nginx.conf:72`), всё остальное → 426
- **Decoy-сайт** на `/` (`nginx.conf:108`) — `relay-server/decoy-site/index.html`,
  279 строк правдоподобного лендинга аналитики. Кто зайдёт браузером на домен —
  увидит обычный сайт.
- Rate limiting, security headers

`infrastructure/`: `setup.sh`, `rotate-domain.sh` (ротация домена при блокировке),
`monitoring.sh`, `cloudflare-setup.md`.

### 2.3 Антицензурные механизмы в сетевом ядре — есть из коробки

Это важно и этим надо пользоваться, а не изобретать заново:

- **`datacenterAddressOverrides`** — `MTApiEnvironment.h:73`. Позволяет подменить адрес
  любого дата-центра. Применяется в `MTContext.m:434` (инициализация набора адресов) и
  `MTContext.m:1022` (построение транспортной схемы: при наличии override он
  **полностью вытесняет** штатные схемы, см. флаг `isAddressOverride` и ветку
  `MTContext.m:1032`).
- **`MTDatacenterAddress`** несёт поле `secret` (`MTDatacenterAddress.h:12`) — значит
  override-адрес может сразу содержать прокси-секрет.
- **fake-TLS** — `MTProxySecretType2` (`MTApiEnvironment.m:233`, парсинг в
  `MTApiEnvironment.m:125`), обработка в `MTTcpConnection.m:851,1252,1715`, проверка
  TLS-заголовка `{0x16, 0x03, 0x03}` в `MTTcpConnection.m:1570`. То есть клиент **уже
  умеет** маскировать MTProto под TLS 1.3 handshake к заданному домену.
- **`accessHostOverride`** (`MTApiEnvironment.h:74`), прокидывается из
  `networkSettings?.backupHostOverride` в `Network.swift:490`.
- **Резолвинг адресов через DoH с domain fronting** — `MTBackupAddressSignals.m`:
  запрос зашифрованной TXT-записи `apv3.stel.com` через `dns.google.com`, причём
  вторая попытка идёт на `www.google.com` с подменённым заголовком `Host`
  (`MTBackupAddressSignals.m:97-98`), и через `mozilla.cloudflare-dns.com`
  (`MTBackupAddressSignals.m:200`), с random padding. Готовый канал доставки
  конфигурации, который очень трудно заблокировать.
- Прокси-настройки уже прокидываются: `Network.swift:485` →
  `withUpdatedSocksProxySettings(effectiveActiveServer.mtProxySettings)`.

### 2.4 Главный пробел

**В MtProtoKit нет WebSocket-транспорта.** Поиск по `submodules/MtProtoKit/` и
`submodules/TelegramCore/Sources/Network/` по `WebSocket` даёт ноль совпадений.
`MTTcpConnection` — это raw TCP (с опциональной fake-TLS обёрткой).

Поэтому **готовый релей-сервер сейчас недоступен iOS-приложению.** Транспорт в
`web-client/src/transport/relay-transport.ts` написан под tdweb (браузерный TDLib) —
к iOS он не применим.

Итог: серверная половина решения готова, клиентская половина для iOS — нет.

## 3. Две развилки реализации

### Путь 1 — fake-TLS MTProto-прокси с вшитым адресом (рекомендую начать здесь)

Идея: **не писать новый транспорт вообще.** Использовать то, что клиент уже умеет
(`MTProxySecretType2`), и вшить адрес в сборку, чтобы пользователю ничего не настраивать.

Серверная часть:
1. Поднять на VPS вне РФ официальный `mtproxy` или `mtg` (Go, проще в эксплуатации) с
   **fake-TLS секретом** — секрет вида `ee<hex16><hex домена>`, где домен — что-то
   нейтральное и реально существующее.
2. Слушать 443. На том же IP держать настоящий сайт на случай активной пробы
   (`decoy-site/` уже готов и переиспользуется).

Клиентская часть (форк):
1. Добавить вшитый список прокси в сборку: `BuildConfig`/`SGSimpleSettings` рядом с тем,
   как сейчас читается `SGSimpleSettings.shared.localDNSForProxyHost`
   (`Network.swift:510`).
2. Включать его как default, если у пользователя нет своих настроек: точка вставки —
   `Network.swift:485`, ветка `if let effectiveActiveServer = proxySettings?...`.
3. Failover по списку и обновление списка через DoH TXT — переиспользовать схему
   `MTBackupAddressSignals.m` (там уже есть domain fronting через Google/Cloudflare).

Плюсы: работающий результат за дни; технология проверенная; сохраняется всё —
секретные чаты, звонки, пуши; релей не видит plaintext.

Минусы: это TCP на 443 к «незнакомому» IP. В РФ с 2024 активно глушат MTProto-прокси по
TLS-фингерпринту и поведенческим признакам (отсутствие реального HTTP-ответа после
handshake, нетипичная длительность соединений). Домен/IP придётся ротировать —
`infrastructure/rotate-domain.sh` под это и написан.

Оценка: **2–4 дня** (сервер — часы, клиент — основная часть, плюс сборка и подпись).

### Путь 2 — WSS-транспорт в MtProtoKit (план Б и долгосрочное решение)

Идея: задействовать уже готовый `relay-server/` — тогда трафик это **настоящий
WebSocket внутри настоящего HTTPS**, и его можно спрятать за CDN.

1. Новый класс `MTWebSocketConnection` рядом с `MTTcpConnection.m` — RFC 6455 поверх
   `NWConnection` (в проекте уже есть
   `NetworkFrameworkTcpConnectionInterface.swift`, можно опереться на него), бинарные
   фреймы, маскирование, ping/pong, фрагментация.
2. Транспортная схема: `MTTransportScheme` сейчас создаётся с
   `transportClass: [MTTcpTransport class]` (`MTContext.m:1026`). Добавить
   `MTWebSocketTransport` и выбирать его для релей-адресов.
3. Конфиг релеев: порт `web-client/src/transport/relay-config.ts` на Swift/ObjC —
   приоритет «вшитый список → DNS TXT → runtime». Формат TXT уже определён.
4. Протокол совпадает с сервером без изменений: WS binary frames ↔ TCP, путь
   `/dc/<id>`, `?token=`.

Плюсы: проходит там, где режут TCP к незнакомым IP; можно поставить Cloudflare перед
релеем (`infrastructure/cloudflare-setup.md`) — тогда для блокировки придётся резать
весь CDN; fingerprint — это fingerprint nginx, а не самодельного протокола.

Минусы: это работа в сетевом ядре, самая чувствительная часть клиента. Ошибки дают
трудноуловимые обрывы соединений. Нужно аккуратное тестирование переподключений,
роуминга Wi-Fi↔LTE, фоновых сессий.

Оценка: **1–2 недели**.

Важно про Cloudflare: он терминирует TLS, но внутри идёт MTProto, который Cloudflare
расшифровать не может. Переписку он не видит — видит только факт и объём соединений.

### Рекомендация

Делать **Путь 1 сейчас**, **Путь 2 — следующим этапом**. Путь 1 даёт работающий
результат за дни и проверяет всю остальную цепочку (сборка, подпись, установка,
`api_id`). Путь 2 переиспользует уже написанный релей и даёт запас прочности, когда
fake-TLS начнут давить.

## 4. Что не решается кодом

Это надо знать до начала, иначе работа упрётся в тупик на последнем шаге.

1. **Установка форка на iPhone.** Форка нет и не будет в App Store. Варианты:
   - Apple Developer Program ($99/год) → TestFlight. Ревью Apple для TestFlight мягче,
     но приложение, целиком маскирующее трафик, — риск отказа.
   - Sideload (AltStore/SideStore + свой Apple ID): бесплатно, но подпись истекает
     каждые 7 дней, нужен периодический re-sign.
   - Своя сборка через Xcode на свой девайс — то же ограничение 7 дней на free-аккаунте.
2. **`api_id` / `api_hash`.** Официальные значения переиспользовать нельзя — аккаунт
   забанят. Нужны свои с my.telegram.org. В репо уже есть коммит `55c5def4 api_id
   refactor`, посмотреть, как это сейчас устроено.
3. **Стоимость и живучесть VPS.** Нужен провайдер вне РФ, желательно не из самых
   популярных (их диапазоны выписывают целиком). Домен не в `.ru` и не у РФ-регистратора.
4. **Ротация.** Один домен рано или поздно заблокируют. `rotate-domain.sh` +
   обновление списка через DoH TXT — не опция, а обязательная часть.

## 5. Фазы работ

**Фаза 0 — решение (нужен твой ответ).** Путь 1 или сразу Путь 2. Способ установки на
телефон (TestFlight или sideload) — от него зависит, сколько возни с подписью.

**Фаза 1 — сервер (0.5 дня).** VPS, домен, Let's Encrypt, `mtg` с fake-TLS, decoy-сайт
на том же IP. Проверка: `curl https://домен/` отдаёт сайт, официальный Telegram с этим
прокси работает.

**Фаза 2 — клиент, Путь 1 (2–3 дня).** Вшитый список прокси, активация по умолчанию в
`Network.swift:485`, failover, обновление списка через DoH TXT по образцу
`MTBackupAddressSignals.m`.

**Фаза 3 — сборка и установка (1–2 дня).** Свой `api_id`, bundle id, подпись, установка
на устройство. Проверка с мобильного интернета РФ-оператора без VPN.

**Фаза 4 — Путь 2, WSS-транспорт (1–2 недели, опционально).** `MTWebSocketConnection`,
`MTWebSocketTransport`, порт `relay-config.ts`, подключение к готовому `relay-server/`,
Cloudflare перед релеем.

**Фаза 5 — эксплуатация.** `monitoring.sh`, автоматическая ротация, несколько релеев в
разных AS.

## 6. Чего я делать не буду

Для полноты, чтобы ожидания совпадали: зеркало сообщений на своём сервере
(вариант «Work OS» из `workos/`) под эту цель не подходит — оно ломает секретные чаты,
звонки и пуши, требует своего APNs, создаёт риск блокировки аккаунта и, главное,
отдаёт всю переписку в plaintext на хостинг. Если когда-нибудь понадобится именно
независимый архив истории — это отдельная задача и отдельный разговор.
